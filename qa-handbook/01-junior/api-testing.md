# Junior: Тестування API

## 1. Що таке API

API (Application Programming Interface) — це контракт, за яким одна програма звертається до іншої. Для веб-застосунків найчастіше це **REST API** по HTTP, що обмінюється даними у форматі **JSON**. Тестувати API можна раніше й швидше, ніж UI: не залежить від інтерфейсу і краще показує, де саме дефект.

### REST у двох словах
- Ресурси мають адреси: `/users`, `/users/17`, `/users/17/orders`.
- Метод HTTP описує дію: GET читає, POST створює, PUT/PATCH змінюють, DELETE видаляє (CRUD).
- Сервер не зберігає стан між запитами (stateless), тому кожен запит містить усе потрібне (наприклад, токен).

### JSON
```json
{
  "id": 17,
  "name": "Olena",
  "email": "olena@example.com",
  "active": true,
  "roles": ["user", "admin"],
  "address": null
}
```
Типи: string, number, boolean, null, object, array. Перевіряйте не лише значення, а й **типи** та **наявність полів**.

## 2. Інструменти
- **Postman** (або Insomnia, Bruno) для ручних перевірок і колекцій.
- **curl** для швидких запитів із терміналу.
- **Swagger UI / OpenAPI** як документація, де часто можна виконувати запити прямо в браузері.

### Приклад у curl
```bash
curl -i -X POST "https://example.com/api/users" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <token>" \
  -d '{"name":"Olena","email":"olena@example.com"}'
```
`-i` показує заголовки відповіді.

### Postman: базові поняття
- **Collection** — набір запитів.
- **Environment** — змінні (`{{baseUrl}}`, `{{token}}`) для різних середовищ.
- Вкладка **Tests** — прості перевірки:
```javascript
pm.test("Status is 201", () => pm.response.to.have.status(201));
pm.test("Has id", () => pm.expect(pm.response.json()).to.have.property("id"));
```

## 3. Що перевіряти в кожному ендпоінті

| Категорія | Приклади |
|---|---|
| Статус-код | Очікуваний 200/201/204; 400/404 на помилки |
| Тіло відповіді | Структура, типи, обов'язкові поля, значення |
| Заголовки | `Content-Type: application/json` |
| Валідація | Порожні поля, неправильні типи, занадто довгі значення, спецсимволи |
| Авторизація | Без токена (401), з чужим токеном/роллю (403) |
| Дані | Після POST ресурс справді з'являється при GET; після DELETE зникає |
| Час відповіді | Звичайні запити не мають «висіти» |

### Мінімальний чек-лист для POST /users
1. Валідні дані → 201, у відповіді id, `email` збігається.
2. Без обов'язкового поля → 400, зрозуміле повідомлення.
3. Невалідний email → 400.
4. Дубльований email → 409 (або інший код за специфікацією).
5. Порожнє тіло та некоректний JSON → 400.
6. Без токена → 401.
7. GET створеного користувача повертає ті самі дані.
8. У відповіді немає чутливих полів (наприклад, пароль).

## 4. Позитивні й негативні тести
- **Позитивні** підтверджують, що очікувана поведінка працює.
- **Негативні** перевіряють, що система коректно відхиляє погані вхідні дані й не ламається (не повертає 500, не показує стек-трейс).

## 5. Як писати баг-репорт для API
Додайте: метод і URL, заголовки (без секретів), тіло запиту, статус-код і тіло відповіді, очікуване за специфікацією, середовище, час запиту. Найзручніше прикріпити запит як cURL.

## 6. Де практикуватися
Публічні тренувальні API: **JSONPlaceholder**, **ReqRes**, **Restful-Booker**, **Swagger Petstore**. Перед використанням перегляньте їхню документацію й обмеження.

## Практика

1. У Postman створіть колекцію з CRUD-запитами до тренувального API й збережіть `baseUrl` як змінну середовища.
2. Для кожного запиту додайте перевірки статусу й наявності ключових полів.
3. Складіть чек-лист із 10 пунктів для одного ендпоінта за шаблоном вище.
4. Навмисно надішліть некоректний JSON і з'ясуйте, яку відповідь повертає сервер. Чи нема там внутрішніх деталей?
