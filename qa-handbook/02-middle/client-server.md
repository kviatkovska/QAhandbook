# Middle: Клієнт-серверна архітектура

Рівень **діагностики й проєктування перевірок**: ви розумієте, як працюють автентифікація, кешування, CORS, бази даних і асинхронні взаємодії, і вмієте знаходити причину проблеми по шарах.

## 1. Еволюція HTTP і мережа

- **HTTP/1.1**: текстовий, одне з'єднання може обробляти запити послідовно.
- **HTTP/2**: мультиплексування кількох запитів в одному з'єднанні, стиснення заголовків.
- **HTTP/3**: працює поверх QUIC (UDP), швидше відновлюється при втраті пакетів.
- **DNS** перетворює доменне ім'я на IP. Проблеми: неправильний запис, кеш DNS, різні відповіді в різних регіонах.
- **TLS handshake** (спрощено): клієнт і сервер домовляються про шифрування, сервер надсилає сертифікат, обидві сторони створюють спільний ключ. Тест-ідеї: прострочений сертифікат, невідповідність домену, слабкі протоколи.

## 2. REST: обмеження й типові дефекти

Ключові ідеї: клієнт-сервер, **stateless**, кешованість, єдиний інтерфейс, шарувата система. Типові дефекти: використання GET для змін, 200 з помилкою в тілі, непослідовні назви полів, відсутність пагінації, різні формати помилок.

**Пагінація:** *offset/limit* (простіше, але проблеми при змінах даних між запитами), *cursor/keyset* (стабільніше на великих наборах). Перевіряйте першу, останню, порожню сторінку, межі `limit`.

## 3. Автентифікація й авторизація

| Механізм | Ідея | Що тестувати |
|---|---|---|
| Session cookie | Сервер зберігає сесію, клієнт має id у cookie | Закінчення, вихід, фіксація сесії |
| API key | Статичний ключ у заголовку | Відсутній/невірний ключ, ротація |
| JWT | Підписаний токен із claims і терміном дії | Прострочення, підміна claims, невалідний підпис, refresh |
| OAuth 2.0 / OIDC | Делегований доступ через провайдера (Authorization Code + PKCE) | redirect URI, scopes, відкликання доступу |

**JWT** складається з header, payload і signature (base64url). Payload не шифрується, тому не клади туди секрети. Перевіряйте, що сервер відхиляє токен без підпису/зі зміненим payload.

**Атрибути cookie:** `HttpOnly` (недоступна JS), `Secure` (лише HTTPS), `SameSite` (обмежує міжсайтові запити), `Expires/Max-Age`, `Domain/Path`.

**Авторизація:** тестуйте не лише ролі (admin/user), а й доступ до **чужих об'єктів** (зміна `id` у URL), горизонтальне й вертикальне підвищення прав.

## 4. Кешування

- `Cache-Control` (`max-age`, `no-store`, `private/public`), `ETag` + `If-None-Match` (відповідь 304), `Last-Modified`.
- Шари кешу: браузер, CDN, reverse proxy, застосунок (наприклад, Redis), БД.
- Типові дефекти: користувач бачить застарілі дані, чутливі відповіді кешуються публічно, після оновлення ресурсу кеш не інвалідується.
- Тест-ідеї: жорстке оновлення (Ctrl+F5) проти звичайного, зміна даних і перевірка, чи оновився кеш, різні користувачі й один URL.

## 5. CORS

**Same-Origin Policy** обмежує звернення скриптів на інші домени. **CORS** дозволяє виняток через заголовки `Access-Control-Allow-Origin` тощо. Для «непростих» запитів браузер надсилає **preflight** (`OPTIONS`). Симптом у консолі: помилка CORS при працюючому API в Postman (бо Postman не застосовує політику браузера). Це налаштування сервера, не помилка клієнтського коду.

## 6. Проміжні вузли

- **Reverse proxy / load balancer** розподіляє запити між інстансами; може додавати таймаути й змінювати заголовки.
- **CDN** віддає статику з найближчої точки.
- **API Gateway** централізує автентифікацію, rate limiting, маршрутизацію.
- Коди **502/503/504** часто вказують на проблеми між проксі й backend (недоступність, перевантаження, таймаут). Тест-ідеї: поведінка при недоступності одного інстансу, sticky sessions.

## 7. Бази даних

- **SQL** (реляційні) і **NoSQL** (документні, ключ-значення, колонкові): обирають залежно від моделі даних і навантаження.
- **ACID-транзакції:** атомарність, узгодженість, ізоляція, довговічність. Тест-ідеї: часткове збереження при помилці, одночасне оновлення одного запису (race condition), блокування.
- **Індекси** прискорюють пошук, але уповільнюють запис; повільні запити видно в логах.
- **N+1 запитів** — типова причина повільних списків.
- Мінімум SQL для QA: `SELECT`, `WHERE`, `JOIN`, `GROUP BY`, `ORDER BY`, `LIMIT`; перевіряйте, що дані справді збереглися, і шукайте дублікати чи «осиротілі» записи.

## 8. Синхронні та асинхронні взаємодії

- **Синхронні** запит-відповідь: клієнт чекає.
- **Асинхронні**: черги повідомлень (RabbitMQ, Kafka), фонові задачі, webhooks, **WebSocket**/**SSE** для оновлень у реальному часі.
- Тест-ідеї: затримка обробки, повторна доставка повідомлення (чи не створиться дублікат), порядок подій, що буде при недоступному споживачі, відображення проміжного стану в UI («Обробляється»).

## 9. Надійність на рівні взаємодії

- **Timeouts**, **retries** (з backoff), **rate limiting** (429 + `Retry-After`).
- **Ідемпотентність**: повторний POST із мережевим збоєм не має створити два замовлення (idempotency key).
- Тест-ідеї: обрив з'єднання посеред запиту, подвійний клік, повторне надсилання форми, повільний backend.

## 10. Діагностика по шарах

1. **Відтворити** і зафіксувати час, користувача, запит.
2. **Клієнт:** Console, Network, cookies/localStorage.
3. **Мережа/проксі:** статус 4xx/5xx, заголовки, час.
4. **Сервер:** логи за час запиту, **correlation/request id** (якщо є), стек-трейс.
5. **Дані:** SQL-перевірка стану, дані, що спричинили помилку.
6. **Конфігурація:** відмінності між середовищами, feature flags, версії.
Результат: повідомлення в тікеті, яке спрямує розробника в потрібний шар.

## Практика

1. У DevTools розкрийте JWT (jwt.io або base64-декодування) та знайдіть термін дії.
2. Знайдіть приклад ETag/304 на будь-якому сайті й поясніть логіку.
3. Відтворіть CORS-помилку локально (простий сервер без заголовків) і виправте.
4. Для сценарію «оплата замовлення» складіть список перевірок на ідемпотентність і таймаути.
5. Напишіть SQL, що знаходить замовлення без позицій у таблиці `order_items`.
