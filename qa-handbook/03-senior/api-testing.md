# Senior: Контракти, безпека, продуктивність і стратегія API-тестування

Рівень **стратегії й керування ризиками API**: ви визначаєте, що й де перевіряти, як зберегти сумісність між командами та як зробити набір тестів довгостроковим активом.

## 1. Стратегія API-тестування

| Рівень | Мета | Приклади |
|---|---|---|
| Unit/компонент | Логіка всередині сервісу | Валідатори, обробники |
| Contract | Сумісність клієнт ↔ сервер | Pact, схеми OpenAPI |
| API-інтеграційні | Реальна взаємодія з БД/залежностями | Створення, читання, бізнес-правила |
| E2E | Критичні бізнес-потоки | Оформлення замовлення |
| Нефункціональні | Продуктивність, безпека, стійкість | k6, ZAP, fault injection |
| Продакшн | Синтетичні перевірки, моніторинг | Health, ключові транзакції |

Принципи: більшість перевірок найближче до коду; E2E мінімум; кожен рівень має чітку мету, щоб не дублювати інші; стратегія враховує ризики, архітектуру й команди.

## 2. Contract testing

**Проблема:** у мікросервісах зміна одного сервісу ламає інший, а E2E-тести повільні й нестабільні.

**Consumer-driven contract testing (Pact):**
1. Споживач (consumer) описує, що очікує від провайдера (запити, відповіді).
2. Генерується **контракт**, який публікується в брокері.
3. Провайдер перевіряє, що його реалізація задовольняє всі контракти споживачів.
4. У CI перевірка **can-i-deploy** блокує релізи, що ламають контракти.

**Provider-driven (схеми):** OpenAPI як контракт, з автоматичною перевіркою відповідності та виявленням breaking changes (інструменти порівняння специфікацій).

Що вважати breaking change: видалення/перейменування поля, зміна типу, звуження допустимих значень, нове обов'язкове поле запиту, зміна семантики коду відповіді. Додавання необов'язкового поля зазвичай безпечне, якщо клієнти толерантні до невідомих полів («Tolerant Reader»).

## 3. Версіонування та сумісність

- Стратегії: у шляху (`/v2/`), у заголовку, через узгодження контенту. Обирайте одну й документуйте.
- **Політика застарівання (deprecation):** повідомлення, період підтримки, заголовки `Deprecation`/`Sunset`, моніторинг використання старої версії.
- Тестуйте **backward compatibility**: старі клієнти проти нового сервера, нові клієнти проти старого (під час поступового релізу).
- Міграції даних і схем БД сумісні з обома версіями коду під час розгортання.

## 4. Governance і якість специфікації

- OpenAPI-лінтери (наприклад, Spectral) перевіряють стиль, обов'язкові поля, приклади.
- Єдині стандарти: іменування, формат помилок (наприклад, RFC 9457 Problem Details), пагінація, ідемпотентність, ліміти.
- Специфікація — частина Definition of Done; зміни проходять рев'ю.
- Інвентаризація API: невідомі «тіньові» ендпоінти це ризик безпеки.

## 5. Безпека API (OWASP API Security Top 10, редакція 2023)

| Ризик | Коротко | Що перевіряти |
|---|---|---|
| Broken Object Level Authorization | Доступ до чужих об'єктів за id | Підміна id, чужі ресурси |
| Broken Authentication | Слабка автентифікація | Токени, брутфорс, скидання пароля |
| Broken Object Property Level Authorization | Зайві/змінювані властивості | Mass assignment, надлишкові поля у відповіді |
| Unrestricted Resource Consumption | Відсутність лімітів | Розмір тіла, rate limit, дорогі запити |
| Broken Function Level Authorization | Доступ до адміністративних функцій | Ролі проти ендпоінтів |
| Unrestricted Access to Sensitive Business Flows | Зловживання бізнес-потоками | Автоматизація покупок, промокодів |
| Server Side Request Forgery | Сервер робить запити за вказаним URL | Валідація URL, внутрішні адреси |
| Security Misconfiguration | Небезпечні налаштування | Заголовки, CORS, відкриті відладочні ендпоінти |
| Improper Inventory Management | Забуті версії й середовища | Старі версії, неопубліковані ендпоінти |
| Unsafe Consumption of APIs | Довіра до сторонніх API | Валідація відповідей зовнішніх сервісів |

Інтегруйте перевірки в CI: SAST/DAST (наприклад, ZAP), сканування залежностей, перевірка секретів, автоматичні тести доступів. Ручне тестування безпеки лишається потрібним для бізнес-логіки.

## 6. Продуктивність API

- Задайте **SLO** (наприклад, p95 < 300 мс при N запитів/с, помилок < 0.1%).
- Типи: **load**, **stress**, **spike**, **soak**; інструменти: k6, JMeter, Gatling, Locust.
- Реалістична модель: розподіл запитів, think time, дані, кеш «холодний/теплий».
- Спостерігайте не лише клієнтську затримку, а й серверні метрики: CPU, пам'ять, БД, черги, GC, пул з'єднань.
- Запускайте полегшені перевірки продуктивності в CI для виявлення регресій; повні тести за розкладом чи перед релізами.

### Мінімальний приклад k6
```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [{ duration: '1m', target: 50 }, { duration: '3m', target: 50 }],
  thresholds: { http_req_duration: ['p(95)<300'], http_req_failed: ['rate<0.01'] },
};

export default function () {
  const res = http.get(`${__ENV.BASE_URL}/api/products`);
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);
}
```

## 7. Асинхронні API та події

- **Webhooks:** перевірка підпису, повторні доставки, ідемпотентність обробника, таймаути, порядок.
- **Брокери повідомлень:** схема повідомлення, версіонування подій, **DLQ** (dead letter queue), повторна обробка, дублікати, порядок у партиціях.
- **Тестування:** публікація тестової події й очікування ефекту з таймаутом (polling), а не фіксований `sleep`; перевірка метрик/логів як частина асертів.
- **AsyncAPI** — специфікація для опису подієвих API.

## 8. gRPC і GraphQL

- **gRPC:** контракт у `.proto`, бінарний протокол, стрімінг; перевіряйте сумісність схеми (не змінювати номери полів), дедлайни, коди статусу gRPC, метадані.
- **GraphQL:** обмеження глибини й складності запитів, вимкнення introspection у prod за потреби, авторизація на рівні полів, N+1, масові запити (batching) як вектор зловживань.

## 9. Стійкість до відмов у API-тестах

- **Fault injection:** затримки, обриви, помилки 5xx від залежностей (Toxiproxy, мок-сервери, service mesh).
- Перевіряйте: таймаути, ретраї без «шторму», circuit breaker, зрозумілі помилки клієнту, відсутність дублювання операцій.

## 10. Тестові дані й середовища

- Стратегія: синтетичні дані, фабрики/білдери, детерміновані ідентифікатори, ізоляція між запусками.
- Анонімізація/маскування prod-даних, відповідність вимогам захисту персональних даних.
- Віртуалізація сервісів для залежностей, які недоступні або дорогі.
- Ефемерні середовища під PR чи гілку; керування конфігурацією як кодом.

## 11. Архітектура API-фреймворку

```
tests/            # сценарії по доменах
  orders/
clients/          # типізовані клієнти API (з OpenAPI-кодогенерацією)
models/           # схеми запитів/відповідей
fixtures/         # дані, токени, очищення
config/           # середовища, секрети з сховища CI
reporting/        # Allure/JUnit, трасування запитів
```
Практики: типізація, кодогенерація клієнтів із специфікації, єдина точка логування запитів (із маскуванням секретів), ретраї лише для відомих тимчасових збоїв, власники тестів, дашборд стабільності.

## 12. Метрики API-тестування

- Покриття ендпоінтів/операцій специфікації (які мають тести).
- Покриття контрактів і розбіжності між специфікацією й реалізацією.
- Стабільність набору (flaky rate), час виконання, час до зворотного зв'язку.
- Дефекти за джерелом: контракт, бізнес-логіка, безпека, продуктивність.
- Використовуйте їх як сигнал для обговорення, а не як ціль.

## Практика

1. Налаштуйте контракт-тест між двома невеликими сервісами (Pact) і спробуйте навмисно зламати контракт.
2. Порівняйте дві версії OpenAPI-специфікації й складіть перелік breaking changes.
3. Складіть матрицю перевірок OWASP API Top 10 для вашого (чи тренувального) API та автоматизуйте три найважливіші.
4. Напишіть k6-сценарій із порогами й запустіть у CI на тестовому середовищі.
5. Змоделюйте збій залежності (503/таймаут) та опишіть очікувану поведінку й тести.
