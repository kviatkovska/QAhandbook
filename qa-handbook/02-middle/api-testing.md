# Middle: Автоматизація та проєктування API-тестів

Рівень **інженерної практики**: тести пишуться кодом, використовують схеми й дані, запускаються в CI та дають стабільний сигнал.

## 1. Специфікація як джерело тестів

- **OpenAPI/Swagger** описує ендпоінти, параметри, схеми та коди відповідей. З нього можна генерувати клієнти, моки й базові тести.
- Перевіряйте **відповідність специфікації**: документація й реальність часто розходяться (поля, коди помилок, обов'язковість).
- Використовуйте **JSON Schema** для перевірки структури відповідей: типи, обов'язкові поля, формати, `additionalProperties`.

## 2. Інструменти для автоматизації

| Підхід | Коли |
|---|---|
| Postman + Newman | Швидкий старт, колекції в CI |
| Python: pytest + requests/httpx | Гнучкість, фікстури, параметризація |
| Java: REST Assured + JUnit/TestNG | Корпоративні проєкти на Java |
| Playwright API testing / Cypress `cy.request` | Єдиний набір для UI+API, підготовка даних |
| Karate, SuperTest (Node) | Декларативні сценарії / Node-проєкти |

### Приклад pytest + requests
```python
import pytest
import requests

BASE_URL = "https://api.example.com"

@pytest.fixture(scope="session")
def auth_headers():
    resp = requests.post(f"{BASE_URL}/auth/login",
                         json={"email": "qa@example.com", "password": "secret"})
    assert resp.status_code == 200
    return {"Authorization": f"Bearer {resp.json()['token']}"}

def test_create_user_returns_201_and_matches_input(auth_headers):
    payload = {"name": "Olena", "email": "olena+1@example.com"}
    resp = requests.post(f"{BASE_URL}/users", json=payload, headers=auth_headers)

    assert resp.status_code == 201
    body = resp.json()
    assert body["email"] == payload["email"]
    assert "password" not in body

@pytest.mark.parametrize("payload", [{}, {"name": ""}, {"email": "not-an-email"}])
def test_create_user_rejects_invalid_payload(payload, auth_headers):
    resp = requests.post(f"{BASE_URL}/users", json=payload, headers=auth_headers)
    assert resp.status_code == 400
```

### Приклад Postman (Tests)
```javascript
const body = pm.response.json();
pm.test("201 Created", () => pm.response.to.have.status(201));
pm.test("Schema valid", () => {
  pm.expect(body).to.have.all.keys("id", "name", "email");
});
pm.environment.set("userId", body.id);   // для наступних запитів
```
Запуск у CI: `newman run collection.json -e env.json`.

## 3. Структура набору API-тестів

- **Шар клієнта**: функції-обгортки над HTTP (одна точка для base URL, заголовків, авторизації).
- **Моделі/схеми** відповідей.
- **Фікстури** для даних і токенів; створюйте дані на старті тесту й прибирайте після.
- **Тести** з чіткими іменами: `test_<дія>_<умова>_<результат>`.
- **Конфігурація** середовищ через змінні (не хардкодьте URL і секрети; зберігайте секрети в CI-сховищі).

## 4. Дані та залежності

- Незалежні тести: кожен створює потрібне й не покладається на порядок.
- Унікальні дані (`email+{uuid}@example.com`) запобігають конфліктам при паралельних запусках.
- **Chaining**: результат одного запиту (id, токен) використовується в наступному, але ланцюжки тримайте короткими.
- **Data-driven**: параметризація набором значень для валідацій і граничних випадків.
- **Моки та заглушки** (WireMock, Mockoon, mock-сервери Postman) ізолюють тести від нестабільних зовнішніх сервісів або підміняють недоступні.

## 5. Що додатково перевіряти

- **Негативні сценарії**: неправильні типи, великі тіла, спецсимволи, unicode, порожні масиви, `null`.
- **Права доступу**: матриця «роль × ендпоінт × очікуваний код».
- **Ідемпотентність** (повтор PUT/DELETE, POST з idempotency key) і **конкурентність** (два одночасних оновлення).
- **Пагінація, сортування, фільтри** разом.
- **Заголовки**: Content-Type, Cache-Control, CORS (для браузерних клієнтів).
- **Помилки**: однаковий формат, без стек-трейсів і внутрішніх деталей.
- **Зворотна сумісність**: додавання поля не ламає клієнтів, видалення чи перейменування ламає.

## 6. GraphQL: коротко

Один ендпоінт (`POST /graphql`), запит описує потрібні поля. Перевіряйте: валідність схеми, відповіді з `errors` (часто з кодом 200), обмеження глибини й складності запитів, авторизацію на рівні полів, N+1 у резолверах.

## 7. Запуск у CI

1. Тести на кожен PR запускаються на ізольованому/стабільному середовищі.
2. Результати у форматі JUnit/Allure видно в пайплайні.
3. Падіння блокує merge лише для стабільних, критичних тестів; нестабільні карантинять і виправляють.
4. Smoke API після деплою на stage/prod (безпечний, неруйнівний набір).

## 8. Нестабільність API-тестів

| Причина | Рішення |
|---|---|
| Спільні дані між тестами | Унікальні дані, створення в тесті |
| Залежність від порядку | Ізоляція, фікстури |
| Асинхронна обробка | Опитування з таймаутом (polling), а не `sleep` |
| Нестабільне середовище | Моки зовнішніх залежностей, health-check перед запуском |
| Жорсткі очікування часу | Розумні порогові значення |

## Практика

1. Напишіть 10 тестів (pytest або REST Assured) для CRUD тренувального API, із параметризацією негативних кейсів.
2. Додайте перевірку JSON Schema для відповіді списку.
3. Налаштуйте GitHub Actions workflow, що запускає тести на кожен push.
4. Підніміть мок-сервер для зовнішньої служби й перевірте, як система поводиться при її помилці 503.
5. Складіть матрицю доступів «роль × ендпоінт» і автоматизуйте її.
