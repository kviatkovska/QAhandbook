# Senior: Розподілені системи та архітектурні ризики

Рівень **системного мислення**: ви розумієте, як архітектура створює ризики, і проєктуєте тестування так, щоб їх виявляти до користувачів.

## 1. Архітектурні стилі й що вони означають для тестування

| Стиль | Особливості | Ризики для якості | Акцент у тестуванні |
|---|---|---|---|
| Моноліт | Один деплой, одна БД | Складні зміни, спільні залежності | Регресія, модульність, швидкі unit |
| Модульний монолітний | Чіткі межі модулів | Порушення меж | Тести меж модулів |
| Мікросервіси | Багато незалежних сервісів | Мережа, версії, узгодженість даних | Контракти, інтеграції, observability |
| Serverless | Функції за подією, керована інфраструктура | Холодний старт, ліміти, локальне відтворення | Інтеграційні тести в хмарі, ліміти |
| Event-driven | Взаємодія через події/черги | Порядок, дублікати, затримки | Ідемпотентність, ретраї, DLQ |

## 2. Взаємодія сервісів

- **Синхронна** (REST, gRPC): простіше, але ланцюжки викликів множать затримки й ризик відмови.
- **Асинхронна** (Kafka, RabbitMQ, SQS): більша стійкість, але складніше відстежувати потік і гарантувати порядок.
- **API Gateway** і **service mesh**: маршрутизація, автентифікація, rate limit, ретраї, mTLS.
- **BFF (backend for frontend)**: агрегація даних для конкретного клієнта.

## 3. Узгодженість даних

- Розподілені системи часто обирають **eventual consistency** (кінцева узгодженість): дані стають узгодженими не одразу.
- **Saga** координує розподілену транзакцію послідовністю локальних кроків із компенсаціями.
- **Outbox-патерн** гарантує публікацію події разом зі зміною в БД.
- Інтуїція **CAP**: при розділенні мережі доводиться обирати між узгодженістю та доступністю.
- Тест-ідеї: що бачить користувач у проміжному стані, чи є компенсація при частковій відмові, чи нема «втрачених» або дубльованих подій, поведінка при повторній доставці й порушеному порядку.

## 4. Шаблони відмовостійкості

| Шаблон | Ідея | Що перевірити |
|---|---|---|
| Timeout | Не чекати нескінченно | Значення адекватні, помилка зрозуміла |
| Retry з backoff + jitter | Повторні спроби без «шторму» | Ліміт спроб, ідемпотентність |
| Circuit breaker | Тимчасово перестати викликати збійний сервіс | Перехід станів, відновлення |
| Bulkhead | Ізоляція ресурсів | Збій одного не валить решту |
| Fallback / graceful degradation | Резервна поведінка | Користувач отримує зрозумілий результат |
| Rate limiting / backpressure | Захист від перевантаження | 429, черги, поведінка клієнтів |
| Idempotency key | Безпечні повтори | Дублі не створюються |

## 5. Observability

- **Логи** (події), **метрики** (числа в часі), **трейси** (шлях запиту крізь сервіси). **OpenTelemetry** — поширений стандарт збору.
- **Correlation/trace id** наскрізний; QA має вимагати його в логах і відповідях.
- **Golden signals:** затримка, трафік, помилки, насиченість.
- Використання в тестуванні: перевірка наявності логів і метрик як вимоги, діагностика падінь, асерти на метрики/події, алерти й дашборди як об'єкт тестування.
- **SLI/SLO/SLA** і бюджет помилок допомагають приймати рішення про релізи.

## 6. Масштабування й продуктивність

- **Вертикальне** і **горизонтальне** масштабування; **stateless** сервіси масштабувати легше (сесії виносять у спільне сховище).
- Кеш-шари: CDN, reverse proxy, застосунок (Redis), БД; ризики: інвалідація, «cache stampede».
- Типи тестів: **load, stress, spike, soak (endurance), scalability**; метрики: затримка за процентилями (p50/p95/p99), пропускна здатність, помилки, використання CPU/пам'яті, черги.
- Тестове середовище має бути репрезентативним; порівнюйте з базовою лінією (baseline) і шукайте регресії в CI.
- Не довіряйте середньому значенню; хвости розподілу (p99) визначають враження користувача.

## 7. Деплой і середовища

- **Контейнери та Kubernetes** (основи): образ, под, сервіс, ingress, конфіги, секрети, проби готовності/живості.
- Стратегії релізів: **blue-green**, **canary**, **rolling**, **feature flags**; відкат і сумісність схем БД (expand/contract міграції).
- **Ефемерні середовища** для PR; стабільне staging; управління тестовими даними (синтетичні, анонімізовані; GDPR).
- Тест-ідеї для релізу: сумісність версій під час поступового розгортання, міграції даних, відкат, прапор вимкнено/увімкнено.

## 8. Безпека архітектури

- **Threat modeling (STRIDE):** підміна, підробка, відмова від авторства, розкриття інформації, відмова в обслуговуванні, підвищення привілеїв.
- Принципи: найменші привілеї, захист у глибину, **zero trust**, шифрування в дорозі й у спокої, керування секретами.
- Перевірки: автентифікація між сервісами, ізоляція тенантів, SSRF, безпечні залежності (SCA), журналювання без чутливих даних.

## 9. Стратегія тестування для розподіленої системи

1. **Unit** у кожному сервісі.
2. **Contract-тести** на межах сервісів (див. [API testing Senior](api-testing.md)).
3. **Інтеграційні** з реальними залежностями там, де це дешево, інакше з віртуалізацією.
4. **Компонентні тести** одного сервісу з усіма залежностями в контейнерах/моках.
5. **E2E** малий набір критичних бізнес-потоків.
6. **Нефункціональні й відмовостійкі** перевірки (навантаження, chaos).
7. **Продакшн-моніторинг** і синтетичні перевірки як частина стратегії.

## 10. Chaos engineering

Контрольовані експерименти для перевірки гіпотез про стійкість: «якщо сервіс X недоступний, замовлення все одно приймаються». Етапи: гіпотеза, обмежений радіус впливу, експеримент, спостереження, висновки. Починайте в безпечних середовищах, автоматизуйте поступово.

## Практика

1. Намалюйте схему потоку «оформлення замовлення» в мікросервісах і випишіть 10 відмов на шляху з очікуваною поведінкою.
2. Складіть план тестів для міграції схеми БД без простою.
3. Визначте SLI/SLO для критичного API та запропонуйте алерти.
4. Опишіть експеримент chaos для залежності від платіжного провайдера.
5. Зробіть мінімальну трасу запиту в локальному стенді з OpenTelemetry (якщо можливо).
